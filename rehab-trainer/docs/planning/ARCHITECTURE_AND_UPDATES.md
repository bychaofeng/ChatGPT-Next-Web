# 架构、提示词与画像更新

整理日期：2026-10-02。代码对照基线：`17fc8af172d3594d54aad0700711565ae3645b75`。下文区分完整目标设计和 v0.3 原型实际取舍；不把接口草案视为已完成实现。

## 1. 总体分工

两个使用入口共用一套训练核心。AI负责候选内容、作答理解、教学解释和讨论线索；程序负责选题规则、固定事实、原始记录、流程、权限、校验、持久化和画像重建。

逻辑模块包括：能力地图、训练调度、题目与病例管理、教学对话、评价与证据管理、知识及内容版本。它们不需要六个服务器或六个模型，第一版可以在一个安卓工程内完成。

当前原型代码映射：

| 职责 | 文件 | 当前边界 |
|---|---|---|
| 数据与画像投影 | `Models.kt` | 八项能力、帮助与重复条件、暂定观察；无认证等级 |
| 蓝图与冷启动调度 | `Content.kt` | 16 道虚构演示题和可解释规则；不是完整专业题库 |
| 训练、评价和记忆流程 | `Engine.kt` | 提交、帮助、争议、线索、调用计数 |
| 本地保存 | `Persistence.kt` | 单进程快照及存储接口；不是已经使用 Room |
| 四组提示词 | `Prompts.kt` | 当前运行时输入输出，与历史 v0.2 草案不完全同形 |
| 网络与返回校验 | `Ai.kt` | HTTPS 聊天补全适配；真实服务联调待验证 |
| 安卓交互与密钥 | `app/` | 平台 View、Keystore 相关代码；不是 Compose 界面 |

源码路径以 [项目首页](../../README.md) 为入口。Room、Compose 是早期考虑过的后续选项，不应在当前实现说明里写成已使用。

## 2. 未知用户怎样起步

目标流程：建立未知状态 → 选择一次低负担探索 → 观察本次表现 → 更新相关证据 → 决定继续探索、补练、验证或接受用户选择。

未知不等于不会。不从年资、措辞、名字或自评分推断资质；没有背景表也能使用。初期误判可以被新证据纠正，保留探索机会防止用户被困在简单题中。

v0.3 的实际简化：首次从目标与优先级任务开始；用户主动选择优先；每三轮保留未知能力探索机会；否则在到期观察、近期不足的适度补练、讨论待验证线索和其他未知能力之间选择。题目家族优先选较少见的，避免连续只换措辞。

这是一组可解释的试用启发式，不是已经校准的智能测量模型。当前题库每能力仅有少量模板，不能宣称覆盖了全身主题或完整难度适配。后续扩充能力细分、前置知识与情境维度时，需增加明确的观测任务和测试，而不是只换一个更强的模型。

## 3. 一次任务的记录结构

完整设计分别保存任务意图、固定题目、当前进度、行动与提交、评价修订、可用证据、画像及复测建议。详见 [训练任务协议](archive/rehab_training_contract_v0_1.md)。v0.3 使用更精简的 `Session`、`Attempt`、`Evaluation`、`Message`、`MemoryBatch`、`Learner` 和 `Snapshot`，不能直接将设计示例作为运行时存档导入。

必须保留的原则：先保存原始提交再请求评价；新答案不覆盖旧答案；提交时可见事实及帮助条件随答案冻结；评价需要引用本次真实内容；画像从有效记录重建；一个病例、一个用户的资料不能串入另一个。

完整设计将教学阶段、暂停/结束状态、评价状态分开。原型的恢复和简单状态不能被描述为完整多阶段状态机已经实现，复杂生命周期仍需设备验收。

## 4. 四组提示词怎样调用

| 组件 | 读取什么 | 返回什么 | 不允许什么 |
|---|---|---|---|
| generate | 程序给定目标、固定蓝图、相关画像摘要和题目暴露 | 候选题面 | 自改病例事实、评分标准、用户等级或评估资格 |
| evaluate | 本次题目、评分要点、答案、提交时信息及帮助 | 逐项候选评价与引用 | 读取旧的强弱印象、偷用后来的答案、直接写画像 |
| coach | 当前题目、允许事实、教学需求、近期讨论 | 讲解、提示或一个适当追问 | 虚构病例信息、无限延长训练、宣称用户已掌握 |
| absorb | 未处理的新消息及允许能力范围 | 待验证线索、续聊摘要 | 把助手解释或“懂了”当独立能力证明 |

四类任务可共用一个模型。长期记录由应用保存，下次只发送需要的片段，不靠一段提示词要求模型永久记住一切。没有实际模型再训练。

历史完整提示词在 [v0.2 文档](archive/rehab_prompts_and_update_rules_v0_2.md)；当前执行内容在 [Prompts.kt](../../core/src/main/kotlin/cn/rehab/trainer/core/Prompts.kt)。修改提示词时保留版本，并与真实返回的结构和语义一起验证。

## 5. 保存、吸收与复测是不同频率

**原始记录：** 提交答案、发送消息、实际展示提示时及时保存。程序完成，不需要模型调用。

**能力观察：** 一次评价通过结构、引用、版本和应用准入检查后，立即重建涉及的能力；不等六轮聊天或当天结束。争议、撤回和不确定评价不能继续作为有效表现。

**讨论摘要：** 有新增讨论才提取，不覆盖原始回答；当前近期消息可以继续用于对话，不必每句都生成长期摘要。

v0.3 的摘要触发采用六轮完整问答、16,000 字符阈值或主动结束时有新内容；单批最多 24 条消息，未处理原文仍保留。历史 v0.2 中“输入预算约70%”是另一项设计参数，不能写成当前代码已经实现的精确 token 预算器。

**复测建议：** 原型用相关帮助后约三天、符合条件的无提示练习后约七天再次观察。日期和轮次都是试用参数，不证明最佳学习规律。到期不生成成功或失败，也不等于创建了现实推送通知。

## 6. 评价如何进入画像

程序顺序：保存提交 → 发起请求 → 核对返回 → 接受为适当层级的观察或暂停核查 → 保存有效评价 → 重建相关投影 → 下次调度读取新投影。

提示后答对表示帮助后进展，刚讲完的变式表示即时巩固，符合内容资格和独立条件的新情境才可能支持独立表现判断；延迟保持还需要新的实际作答。

当前演示题未医学审核，所有观察均为暂定，`verifiedIndependent` 始终为零。原型里的“无提示练习表现”不能换名宣传成已认证能力。

同一次提交重复评价不能制造新样本。评价有争议时暂停相关影响；核查后恢复或修订，再重建画像。聊天线索只能影响“下一步值得验证什么”，不能直接加减独立计数。

## 7. 模型与存储的工程边界

Key仅用于传输鉴权，不进入提示词、学习存档、导出或日志。当前默认自带Key；将来若统一提供密钥，需另建受保护的后端，不把共享Key放进APK。

接收JSON后仍须核对字段、ID、版本、引用和状态。格式有效不代表专业正确；模型自称有信心不授予写入权限。限制请求次数、重试与输出大小，拒绝越权字段，不跟随重定向发送Key。

原型使用本地快照与单请求队列；完整事务、跨进程冲突、大数据量、备份恢复及数据库迁移是后续工程项。接口失败应保留待评价，不能记用户答错；晚到结果只对应旧提交，不覆盖新答案。

当前滚动24小时调用尝试上限默认30，可在界面设置范围内调整。它限制的是请求数量，不是精确货币预算，也不保证超时重试不会被供应商计费。切换档案不能重置共用调用额度。

## 8. 扩展而不绑死

模型适配层与业务逻辑分离；题目和解剖资源通过结构ID关联；病例事实与学习画像隔离；原始证据与可重建投影分离。

先验证主流程，再按需要引入审核内容包、稳定测评题、语音/二维图、3D、独立模拟病例讨论、授权后的真实病例功能、Room迁移或账号同步。不是为了架构完整而同时建设全部服务。
